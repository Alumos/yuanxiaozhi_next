# 公共 03 · 模型接口与缓存

> 三个环节共用同一个模型网关模块 `internal/llm`。各环节只写“场景”（提示词 + 输出格式 + 校验 + 兜底），不直接调接口。

---

## 1. 网关

- 协议：OpenAI 兼容的 `POST {YXZ_TEXT_BASE}/chat/completions`，**必须流式**（`stream: true`）。
- 地址、密钥、模型名只从环境变量读取（`公共/01` 第 9 节）。密钥不写进文件、不打印到日志、不发给前端。
- 沿用旧平台在课堂网关上实测过的做法（`../yuanxiaozhi/server/internal/provider/chat.go`）：
  - 只用 HTTP/1.1。网关在 HTTP/2 下会出错。
  - 网关约 60 秒没有数据就断开，所以必须流式。
  - `response_format: json_object` 可用，严格的 `json_schema` 不生效。新系统的推荐场景改用**按行输出**（见 `计算/02`），不依赖 JSON 模式。
  - 识图模型默认开思考，要显式设置。
- 流式解析：按 SSE 读 `data:` 行，把 `delta.content` 和 `delta.reasoning_content`（有些模型叫 `reasoning`）分开交给场景处理。

## 2. 思考程度

每个场景在配置里设 `effort`：`off | low | medium | high`。不同的模型服务商，参数写法不一样，由网关模块按 `content/common/config.json` 里的 `effort_style` 统一转换：

| `effort_style` | `off` | `low` / `medium` / `high` |
|---|---|---|
| `openai` | 不传 `reasoning_effort`（或用不带推理的模型） | `"reasoning_effort": "low" / "medium" / "high"` |
| `qwen` | `"enable_thinking": false` | `"enable_thinking": true, "thinking_budget": 512 / 1500 / 4000` |
| `deepseek` | `"thinking": {"type": "disabled"}` | `"thinking": {"type": "enabled"}`，再用 `max_tokens` 限制总量 |
| `none` | 什么都不传 | 什么都不传（这个模型不支持调节） |

- **默认值**：推荐场景 `low`，画图说明书 `off`。数字可以在 `/admin` 里临时改。
- 开了思考后，模型的推理过程（`reasoning_content`）只发给**大屏**的“草稿纸”小窗（见 `计算/03`），不发给平板，也不写进学生能看到的地方。
- 推理内容也是流式的，能让连接一直有数据，所以开思考不会触发 60 秒断开。但总耗时会变长，开工前要实测（第 7 节 V2）。

## 3. 上下文缓存（降低开销的关键）

主流模型服务都有**前缀缓存**：如果这次请求开头的一大段内容，和最近某次请求开头的内容**一字不差**，这一段就不用重新计算。命中部分计费便宜很多，返回也更快。不同服务商的情况：

- DeepSeek：自动缓存，命中部分单独计价。
- OpenAI：前缀达到 1024 token 以上才会自动缓存；可以用 `prompt_cache_key` 让相同前缀的请求落到同一处缓存。
- 通义千问：有隐式缓存。

本系统按这个原理组织所有提示词：

```
messages[0]  system  ← 固定前缀：人设 + 任务规则 + 输出格式 + 示例 + 书库索引（几千到两万 token）
                        全班 25 台平板完全相同 → 第一次写入缓存，之后都命中
messages[1]  user    ← 变化部分：这位学生的 5 轮选择记录、本地计算结果、候选书（一两千 token）
messages[2…]         ← 同一个学生的追问（“不准，再想想”）接在后面，前面的全部内容又成为缓存前缀
```

**规则（写进代码审查清单）**

1. 固定前缀里**不允许出现**任何会变的内容：时间、座位号、随机数、学生数据。
2. 书库索引按 `id` 排序，用固定格式输出。同一份书库生成的文本每次都一样。启动时计算前缀的哈希值，写进日志。
3. 同一个场景的所有请求，`model`、`temperature`、`effort` 保持一致（有些服务商把这些参数也算进缓存键）。
4. 用 OpenAI 风格的网关时，`prompt_cache_key` 设为“场景名 + 前缀哈希”。
5. **预热**：
   - 服务器启动时，对每个带长前缀的场景发一次请求（`max_tokens: 1`）；
   - 教师在大屏点“开始本环节”时再发一次；
   - 预热是否成功显示在 `/admin` 上。
6. **统计**：从返回的 `usage` 读命中 token 数（字段名可能是 `prompt_cache_hit_tokens` 或 `prompt_tokens_details.cached_tokens`），按场景累计命中率，显示在 `/admin` 上。

**学生看不出来**：缓存的只是“说明书”和“书库”这些共用内容。每个学生的选择记录、计算结果、候选书都是自己的，模型每次都真实地针对这些内容推理，所以每个人拿到的推荐和理由都不一样。

## 4. 场景

场景定义在各环节的 `content/<环节>/scenes.json`：

```json
{
  "jisuan.recommend": {
    "prefix": ["common/persona.md", "jisuan/prompts/recommend_rules.md"],
    "prefix_role": "user",
    "user_template": "jisuan/prompts/recommend_user.md",
    "output": "lines",
    "effort": "low",
    "temperature": 0.7,
    "max_tokens": 6000,
    "first_line_timeout_s": 25,
    "timeout_s": 35,
    "validate": "jisuan.ValidateRecommend",
    "fallback": "jisuan.LocalRecommend",
    "stream_to": ["student", "screen"]
  }
}
```

- `prefix_role: user`：固定前缀放在第一条用户消息开头（课堂网关会丢 system）。
- 两道超时：`first_line_timeout_s` 内没有收到第一行有效输出，整次走 `fallback`；`timeout_s` 到了还没结束，缺的部分由 `fallback` 补齐。
- `max_tokens` 包含推理 token，留足余量，避免推理太长把正文挤掉（实测 `medium` 出现过）。
- 书库索引 `@books_index` 只在网关支持缓存时才考虑放进前缀，目前不放。
- `output`：`text`（文字）| `lines`（按行协议）| `json`。
- `fallback` 可以是兜底文件，也可以是本地函数。推荐场景用本地算法生成兜底结果，内容同样来自真实计算。

## 5. 排队与并发

- 全局并发上限 `max_concurrency`（默认 10，按网关实测再调整）；每个环节还有自己的上限。
- 遇到 429 或 5xx：自动把并发减半，30 秒后逐步恢复；同一请求最多重试 1 次。
- **优先级**：教师演示 > 学生首次请求 > 学生追问。
- 排队时，学生端不显示“排队”，而是继续播放前面几段本地计算的动画（`计算/03` 第 4 节）。排队等待的时间被动画盖住了。
- 同一座位同时只允许一个请求在进行。

## 6. 兜底、回放、模拟

| 情况 | 处理 |
|---|---|
| 超时（场景 `timeout_s`）或校验两次不通过 | 用场景的 `fallback`。日志记一次兜底，`/admin` 兜底计数加一 |
| 回放模式 | 按“场景 + 输入特征”找彩排录下的回答。推荐场景的输入特征 = 偏好前三标签 + 候选书集合，取重合度最高的一条，再校验候选书是否都在本次候选里；不在就用本地兜底 |
| 模拟模式 | 不联网，直接用本地兜底函数，并模拟流式输出的速度（每行 300–600ms） |

兜底结果在学生端和正常结果**完全一样**，不加“参考”标记。教师从 `/admin` 和大屏右下角的小圆点能看到。

## 7. 开工前的验证

> **2026-11-07 已在课堂网关上实测**（模型 `YM ·DeepSeek-V4.1`，见 `计算/自检/测试报告.md`）：
> - V1 缓存：基本不命中（2–7%），**不依赖缓存**；
> - V2 思考程度：`reasoning_effort` 有效，`low` 平均 14 秒，`medium` 平均 20 秒、偶尔 50–80 秒；
> - V4 格式：提示词放在用户消息里时 6/6 正确，放在 system 时网关有 4/10 会丢掉 system。
>
> 因此，**所有场景的固定提示词都放在第一条用户消息的开头**，不用 system 角色。

| 编号 | 验证内容 | 通过标准 | 不通过怎么办 |
|---|---|---|---|
| V1 | 课堂网关是否透传前缀缓存 | 第二次相同前缀的请求，`usage` 显示命中 token ≥ 前缀的 80%；或首字时间明显缩短 | 换支持缓存的模型或网关；不行就把书库索引移出前缀，只发候选书的摘要（开销仍然可控，见 `计算/02` 第 8 节） |
| V2 | 思考程度参数是否生效、耗时多少 | `off/low/medium` 三档的推理 token 数明显不同；`low` 档推荐场景在 15 秒内完成 | 换 `effort_style`；或推荐场景用 `off` |
| V3 | 25 个请求同时发出 | 全部在 30 秒内完成，没有失败 | 降低并发；把动画的最短时长加长 |
| V4 | 按行协议的遵守率 | 50 次调用中格式正确 ≥ 48 次 | 加示例；放宽解析规则 |
