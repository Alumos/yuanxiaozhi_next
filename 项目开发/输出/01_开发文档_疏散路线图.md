# 输出 01 · 开发文档：疏散路线图（`/shuchu`）

> 课上的活动：活动三“疏散路线图发布会”（教学流程见上一级 `01_教学设计.md`，信息卡、班级卡等资源见 `02_教学资源清单.md`）。
> 公共部分：[架构与部署](../公共/01_总体架构与部署.md)｜[界面风格](../公共/02_界面风格规范.md)｜[模型接口与缓存](../公共/03_模型接口与缓存.md)

---

## 0. 一页看懂

- 6 个小组各负责一个六年级班。学生给元小智“喂信息”（勾选信息卡、写对路线图的要求），元小智在**校园平面图上画出逃生路线**，发回一张“改好的地图”。
- **实现路径不变**：底图是原来的 HTML 校园平面图（`素材/校园/校园结构图.html`，已移植为 SVG 渲染代码）。路线用 SVG 叠加在底图上，而不是让生图模型生成图片。
  - 大模型只输出一份“画图说明书”（JSON）；
  - 前端按说明书把路线、箭头、标志画到平面图上，再栅格化成 JPEG，作为对话里的一张图片发给学生。
  - 学生看到的就是“元小智把地图改好发回来了”（这是硬性要求）。
- 本环节突出**输出**：同样的输入，输出可以是文字、路线、图；输出要给特定的人看（低年级、家长、消防员）；输出带有概率性（“问 5 次”）。但一个完整的 AI 系统仍然包含三个环节，所以计算部分用规划器真实计算，在大屏上慢放。

## 1. 课堂流程（活动三，约 11 分钟）

| 步骤 | 大屏 `/shuchu/screen` | 学生平板 `/shuchu/` | 系统动作 |
|---|---|---|---|
| 发布任务 | V0 任务发布：教师扮演“消防队长” | 请看大屏 | 教师演示提问“请为六年级规划疏散路线图”（不给任何信息），元小智会反问需要哪些信息 |
| 喂信息 | V1 各组提交状态 | 小组任务：勾选信息卡、写要求、提交 | — |
| 看计算 | V2 规划器慢放 | 本组候选路线和数字 | 运行规划器；慢放到楼梯口第一次变红时自动暂停 |
| 拿图、改图 | V3 作品墙 | 收到路线图；可以改要求，再出第 2 版 | `route_draw` 调用；栅格化后上传 |
| 发布会 | V4 逐张验收 | 请看大屏 | 系统核验；教师点“通过”，盖章 |
| 问 5 次 | V5 预测投票 → 5 张图并排 | 预测投票 | 同一输入连续生成 5 次（温度 1.0） |

## 2. 学生端（平板，每台独立）

### 2.1 每台平板独立（2026-11-09 改）

- 座位号在 `seats.json` 里对应小组，小组决定这台平板负责哪个班。**每台平板有自己的一份状态**（勾选、要求、对话、各版路线图），同组其他平板看不到、也改不了。服务器只把更新推给这台平板自己（`student:<座位号>`）。
- 每台平板同一时间只有一个“生成”在进行，最多 5 版。
- 全校规划：每个班用**该组最近一次请元小智画图的那台平板**的勾选来计算；正在提问的那台平板用它这次的勾选。
- 大屏按 6 个班汇总：V1 显示每张信息卡有几台勾了、组里哪几台已拿到图；V3 / V4 每个班列出组内每台平板的最新一版（按座位号切换），验收针对那一台；V5 “问 5 次”用该组最近一次提交的输入。

### 2.2 布局

左边是任务区，右边是元小智对话区（`ChatPanel`）。

**任务区**
1. 班级卡：班级、楼栋、楼层、位置、人数（来自 `classes.json`）。
2. 验收标准：路线沿道路、不穿楼、终点是集合点、楼梯不拥堵、标出安全提醒。
3. 6 张信息卡，可以勾选，每张后面可以补一句话：

   | 信息卡 | 给了 | 没给（规划器的行为） |
   |---|---|---|
   | ① 班级位置和人数 | 起点和人数 | 无法计算，元小智反问 |
   | ② 楼梯位置 | 用真实楼梯 | 按“楼栋两端”猜，可能猜错 |
   | ③ 道路和距离 | 在道路网上算最短路 | 用直线连接，可能穿过楼房 |
   | ④ 拥堵情况 | 计入共用楼梯的排队时间 | 只看距离 |
   | ⑤ 集合点 | 终点是集合点 | 取“最近的空地”，可能不对 |
   | ⑥ 安全规则 | 说明里带安全要求 | 可能缺少安全提醒 |

4. “对路线图的要求”输入框，加提示词快捷短语：
   - 给谁看：一年级小朋友 / 家长 / 消防员；
   - 颜色、线型、箭头、标志、主题。
   可以打字，也可以用平板输入法的语音输入。

**提交**：消息里附带“校园平面图.jpg”的缩略图，看起来就是学生发了一张图给元小智。

### 2.3 收到路线图

- 对话区出现一张图片（JPEG）和一句话：“改好了！”，再加一句元小智的说明（说明书里的 `explain`）。
- 点图片放大：点哪儿放哪儿，可以双指缩放、拖动，双击还原（`ZoomViewer`，移植旧平台）。
- 生成过程中，图片位置先显示底图，上面有一层“正在修改”的效果：路线沿路径逐段描出（`stroke-dashoffset`），标志依次落下，约 2 秒。完成后再换成栅格化的 JPEG。这一段让学生**看着元小智在图上改**。
- **第 2 版**：学生补充信息或修改要求后再次提交。如果改的是信息卡，规划器只为本组重新计算，其他组不变。第 1 版和第 2 版用标签切换，也可以并排看。
- **再试一次**：图片下方的“再试一次”按钮（公共组件 `RetryButton`）。
  - 用**完全相同的输入**再调用一次 `route_draw`（温度 1.0），生成新的一版，标为“第 n 版 · 再试”。
  - 每台平板最多 5 版。同一时间只能有一个生成在进行。
  - 学生会自己发现：同样的要求，元小智两次画出来的颜色、标志、甚至路线可能不一样。这是在平板上预演大屏上的“问 5 次”。
  - 新增接口 `POST /api/shuchu/group/retry`（基于最近一版的输入），SSE 事件同 `ask`。

## 3. 计算：规划器（服务器真实计算）

**输入**：本组勾选的信息卡（只用给出的信息），以及全班其他组的选择（仅在给了④时使用）。

**模型**
- 道路网：节点（教室门口、楼梯、出口、路口、集合点）和边（长度）。
- 步行用时 = 路径长度 ÷ 步速（默认 1.2 米/秒）。
- 楼梯排队 = 使用这部楼梯的总人数 ÷ 楼梯每秒通过人数。
- 总用时 = 步行 + 排队。

**过程**
1. 每个班在道路网上找 2–4 条候选路线（不同楼梯、不同出口），每条记录距离、用时、楼梯、拥堵程度。
2. 给了④的小组，会考虑别的班选了哪部楼梯：
   - 多个组轮流调整，每轮把用时最长的班换到更快的楼梯，最多 5 轮，直到不再变化；
   - 每轮都记录下来，供大屏慢放。
3. 每组得到推荐路线和备选路线。

**计算轨迹**（`PlanTrace`）：每一轮每个班的路线、各楼梯的人数和颜色（绿 / 黄 / 红）、第一次出现红色的时刻。

> 旧平台的“行远楼二楼 729 种方案”逐一比较的模型（`../yuanxiaozhi/server/internal/app/grid.go`）可以作为备选：如果教师希望在输出环节也突出“计算量大”，可以替换掉这里的轮流调整。默认用轮流调整，因为它更好讲。

## 4. 输出：画图说明书 → SVG → JPEG

### 4.1 场景 `shuchu.route_draw`

- **输入**：本组的信息卡和补充、规划器的候选路线（含数字）、对路线图的要求。
- **固定前缀**：人设 + 画图说明书规则 + 道路网节点表（全班相同，命中缓存）。
- **输出**：画图说明书，`json_object` 模式，后端校验必需字段。`effort: off`。
- **格式**（沿用旧平台已验证的格式，`../yuanxiaozhi/web/src/shared/map/route.ts`）：

```json
{
  "path": ["C63", "J2", "Q3E", "E1", "F0"],
  "line": { "color": "绿色", "width": "粗", "style": "实线", "arrow": "燕尾" },
  "markers": [
    { "type": "安全出口", "at": "E1" },
    { "type": "红旗", "at": "F0", "color": "红色" },
    { "type": "文字", "at": "Q3E", "text": "靠右慢行" }
  ],
  "numbers": true,
  "title": "六（3）班疏散路线",
  "labels": "只留关键",
  "theme": "卡通",
  "audience": "一年级小朋友",
  "explain": "从东楼梯下楼，沿主路去操场，转弯处都标了序号。"
}
```

| 字段 | 取值 |
|---|---|
| `path` | 只能是道路网节点编号 |
| `line.color` | 11 种：默认、绿色、红色、橙色、蓝色、紫色、黄色、粉色、青色、黑色、棕色 |
| `line.width` | 细、中、粗、特粗 |
| `line.style` | 实线、虚线、点线、双线、发光 |
| `line.arrow` | 三角、燕尾、脚印 |
| `markers[].type` | 五角星、红旗、安全出口、暂停使用、文字、圆圈、警告、小人、灭火器、对勾、爱心 |
| `theme` | 默认、简洁、醒目、卡通、夜间、黑白 |
| `labels` | 全部、只留关键 |

### 4.2 渲染

- 平板和大屏用**同一个前端函数** `renderRoute(spec, graph, options)`：生成底图 SVG + 路线层 SVG。移植 `campus.ts` + `route.ts`。
- 栅格化：SVG → `<img>` → Canvas → JPEG，宽 1536，质量 0.85，约 150–250 KB；上传到服务器，作为对话里的图片。
- 大屏作品墙和“问 5 次”直接用 JPEG，避免同时渲染多张复杂 SVG。“问 5 次”的 5 张图由大屏浏览器栅格化。
- 核验标记和验收印章用 SVG / CSS 叠加在 JPEG 上，不改原图。
- 学生默认看不到画图说明书。教师在大屏操作条里可以打开“显示说明书”，用来讲“它其实是写了一份说明书，再由程序画出来”。

### 4.3 核验（服务器）

移植 `../yuanxiaozhi/server/internal/campus/campus.go` 并扩展到全校道路网：
- 路线的每一段都是道路网上的边；
- 不穿过楼房的多边形；
- 起点是本班教室门口，终点是集合点；
- 经过的楼梯没有被标为“暂停使用”；
- 和规划器的推荐相比：用时是否明显更长、是否造成拥堵。

核验结果在发布会上揭晓，不在学生拿到图时提前显示。

## 5. 大屏（`/shuchu/screen`）

| 视图 | 内容 |
|---|---|
| **V0 任务发布** | 消防队长的任务卡；教师演示提问的对话气泡 |
| **V1 提交状态** | 6 个小组卡片：勾了哪几张信息卡、要求写了多少字、是否已提交 |
| **V2 规划器慢放**（放在计算面板里） | ①平面图淡出、道路网浮现 → ②每个班的候选路线依次闪过，标出距离 → ③楼梯口按人数变色：绿 → 黄 → 红，人群点阵移动（参考旧平台 `GridCanvas.vue`）→ ④**第一次出现红色时自动暂停**，教师让学生先判断“该让哪个班换楼梯”，按 `P` 继续 → ⑤调整：某个班换楼梯，红色消退 → ⑥定稿 |
| **V3 作品墙** | 6 个班的最新路线图（JPEG），实时更新；第 1 版和第 2 版可以切换 |
| **V4 发布会验收** | 点某张图放大，叠加核验标记；教师点“通过 / 不通过”；通过就盖“验收通过”红章，作品墙上这张图保留印章 |
| **V5 问 5 次** | ①选一个小组 → ②学生平板出现预测投票“5 次会一样吗？”，大屏显示票数 → ③教师点“开始”，用该组完全相同的输入连续生成 5 次（温度 1.0）→ ④5 张图依次出现、并排 → ⑤统计条：走了哪部楼梯各几次、用了几种颜色和标志、核验没通过几次 |

如果真实结果 5 次完全一样，操作条上会提示“换一个信息较少的组”，或者播放彩排时录下的“问 5 次”。

## 6. 数据文件

校园平面图的渲染代码放在前端 `web/src/shuchu/map/`（来自 `素材/校园/校园结构图.html`），不放在 `content/` 里。

```
content/shuchu/
├─ campus/road_graph.json     道路网：节点、边、楼栋多边形、集合点（要扩充到全校，旧平台只覆盖了一个班的路线）
├─ campus/classes.json        6 个组对应的班级：楼栋、楼层、位置、人数、起点节点
├─ campus/stairs.json         各楼梯每秒通过人数
├─ campus/rules.md            学校消防疏散规定（信息卡⑥）
├─ cards.json                 6 张信息卡的文字、“没给”时的提示
├─ chips.json                 提示词快捷短语
├─ prompts/route_rules.md     画图说明书规则（固定前缀）
├─ scenes.json
└─ fallback/route_draw/*.json 每个班一份兜底说明书
```

**`road_graph.json` 示例**

```json
{
  "nodes": [{ "id": "Q3E", "name": "清源楼东楼梯", "kind": "stair", "building": "清源楼", "x": 1060, "y": 745, "rate": 1.5 }],
  "edges": [{ "from": "Q3E", "to": "E1", "length": 18 }],
  "buildings": [{ "name": "清源楼", "polygon": [[672,713],[1097,713],[1097,780],[672,780]], "stairs": ["Q3W","Q3E"] }],
  "assembly": "F0"
}
```

**`classes.json` 示例**

```json
[{ "group": 1, "class": "六（3）", "building": "清源楼", "floor": 3, "position": "东头", "people": 45, "start": "Q3_C3" }]
```

`yxz check` 校验：班级起点节点存在；道路网连通；每个班至少有 2 条不同楼梯的路线；兜底说明书全部能通过核验。

## 7. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/shuchu/group` | 本组状态：班级卡、信息卡勾选、要求、版本列表 |
| POST | `/api/shuchu/group/cards` | 勾选或取消信息卡、写补充，广播给同组 |
| POST | `/api/shuchu/group/ask` | 提交。规划器计算 + `route_draw` 调用，响应体是 SSE：`plan`（候选路线）→ `spec`（说明书）→ `done` |
| POST | `/api/shuchu/group/image` | 上传栅格化后的 JPEG（版本号） |
| POST | `/api/shuchu/vote` | 问 5 次的预测投票 |
| GET | `/api/shuchu/screen/state` | 大屏全部状态（教师口令） |
| POST | `/api/shuchu/screen/control` | `{action: run_plan\|continue\|approve\|reject\|five_start\|vote_open\|vote_close\|reset, …}`（教师口令） |

SSE 推送：`group_update`（同组）、`plan_trace`、`gallery_update`、`verdict`、`vote_update`、`five_item`（大屏）。

## 8. 并发与时间

- 规划器全班一起算，< 100ms。
- `route_draw` 6 个组并发，每次 10–25 秒（`effort: off`）。生成时平板显示“正在修改图片”的效果。
- “问 5 次”5 个请求并发，**不共享结果**。

## 10. 验收

1. 6 个组从提交到收到路线图 ≤ 60 秒（实时模式）。
2. 说明书里的颜色、线型、箭头、标志、主题要求，在图上全部体现。
3. 核验能发现：穿楼、终点不对、走了暂停使用的楼梯。
4. V2 慢放第一次出现红色时自动暂停，按 `P` 继续。
5. 同组的平板互不影响：一台勾选、提问，其他平板看不到；大屏汇总 ≤ 1 秒更新。
6. 平板上点图放大流畅，旧款平板帧率 ≥ 30；送到浏览器的图片 ≤ 300 KB。
7. 断网后切到回放模式，全流程照常走完。
